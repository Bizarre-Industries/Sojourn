# Sojourn — v0.1 audit

Codename: **Sojourn audit**. Scope: end-to-end gap analysis against the
public v0.1 spec (`docs/ARCHITECTURE.md`, `docs/SUPPORTED_MANAGERS.md`,
`docs/FUTURE.md`, repo README, the v0.1 design PDF). Output: the missing
backend features, architectural gaps, GUI gaps, and doc gaps that need to
land before, during, or after v1 ship — with priority ranking.

This document is the single consolidated companion to the existing
`ARCHITECTURE.md` and `FUTURE.md`. It is meant to be read once, mined for
issues, and trimmed down as items ship.

## 2. Backend feature gaps

### 2.1 mpm features not used

`MPMService` per `ARCHITECTURE.md` §5.1 only exposes `installed`, `outdated`,
`search`, `managers`, `backup`, `restore`. mpm 6.x has more, much of which is
free leverage for Sojourn.

| ID    | Feature                                                    | Severity | Notes                                                                                                                                                                                                                    |
| ----- | ---------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 2.1.1 | `mpm sbom --spdx` / `--cyclonedx`                          | H        | Commit a CycloneDX file alongside `packages.toml` on every push. Pairs with the existing OSV/GHSA cross-reference plan for cooldown bypass — same advisory feed, same data shape. Free supply-chain artifact. mpm 5.18+. |
| 2.1.2 | PURL specifiers (`pkg:npm/left-pad`)                       | M        | `packages.toml` per-machine override schema in §6 reinvents disambiguation between same-name packages across managers. | 2.1.3 | `mpm sync` (registry metadata refresh)                     | M        | Wire into the daily background activity alongside `outdated`.                                                                                                                                                            |

### 2.3 Native replacement decisions

Should Sojourn drop mpm? **No.** Selective native is correct. Decision:

| Manager              | Path                                                        | Rationale                                                                                                                                    |
| -------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `brew`               | Native `BrewService`                                        | 80%+ of installed packages on a Mac dev machine. Stable JSON API (`brew info --json=v2`). Unlocks taps, services, Brewfile interop natively. |
| `cask`               | Native `CaskService` (sibling of `BrewService`, shared CLI) | Same CLI as brew. Cask metadata exposes `artifact_dependencies`.                                                                             |
| `mas`                | Native `MasService`                                         | ~80 LOC. Trivial CLI surface.                                                                                                                |
| `pip`, `pipx`, `uvx` | Keep mpm                                                    | mpm absorbs interpreter resolution, `--user` / `--break-system-packages` semantics, virtualenv detection.                                    |
| `npm`, `yarn`        | Keep mpm                                                    | mpm absorbs workspaces, lifecycle-script gating, registry auth, classic-vs-berry split.                                                      |
| `gem`, `composer`    | Keep mpm                                                    | scope-mismatch bugs are real (mpm's `gem` fix #389 — removed `--user-install` so list/outdated scopes match).                                |
| `cargo`              | Keep mpm                                                    | No outdated either way; equal cost.                                                                                                          |
| `vscode`             | Keep mpm (consider native later)                            | Trivial CLI but mpm is no slower.                                                                                                            |

The five managers where going native is roughly free (mas, vscode, cargo,
pipx, uvx) don't _gain_ anything beyond mpm — they're a wash. The five
where mpm clearly earns its keep (pip, npm, yarn, gem, composer) are
exactly the ones that would re-discover years of version-parsing and
scope-handling fixes if rewritten. Native for cheap managers exists to
**prove the plugin protocol**, not to replace mpm.

### 2.7 Plugin protocol

`FUTURE.md` lists "Plugin system for custom service actors" as a future
item. This audit promotes it because it is the only thing that makes
"support as much as possible" actually safe.

Concrete shape:

```
~/Library/Application Support/Sojourn/plugins/
└── mise.sojourn-plugin/
    ├── manifest.toml         # name, version, capabilities, tier default
    ├── plugin.swift          # protocol-conforming actor (or)
    └── plugin.sh             # shell-script implementing the protocol
```

JSON-over-stdio protocol (matches the IPC-not-linking invariant in
`docs/LICENSING.md`):

- `installed` → `{packages: [{id, version, name?}]}`
- `outdated` → `{packages: [{id, installed, latest}]}`
- `install`, `remove`, `upgrade`
- `manifest` → capability flags

Out-of-process is the default. In-process Swift bundles inherit plugin
crashes and licensing concerns into Sojourn's process; subprocess JSON-RPC
preserves the GPL-3 firewall.

Severity: **H** (architectural unblocker for the long tail).

## 3. Architectural gaps

The v0.1 module layout per `ARCHITECTURE.md` §11 is mostly right
(actor-per-CLI in `Services/`, `JobRunner` separate, `@Observable` AppStore
without TCA, IPC-not-linking invariant). The gaps below are about what's
missing or scattered.

### 3.1 Module-level

| ID     | Gap                                       | Severity | Fix                                                                                                                                                                                                                                                                                                                                                                  |
| ------ | ----------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 3.1.1  | No `Models/` module                       | H        | All value types (`Package`, `ManagerSnapshot`, `ManagerID`, `AutoUpdateTier`, `HistoryEntry`, `Job`, `BootstrapState`, `MachineMetadata`, `ToolInventory`, `ApplicationRegistry`) live in one place. Unblocks 3.2.1.                                                                                                                                                 |
| 3.1.2  | No `Policy/` module                       | H        | Cooldown decisions, OSV cross-reference, tier classification are pure functions buried inside `SyncCoordinator`. Extract to `Policy/CooldownPolicy.swift`, `Policy/AdvisoryService.swift`, `Policy/TierClassifier.swift`. Pure-function policy with actor-based I/O is the testable shape.                                                                           |
| 3.1.3  | `BootstrapService` is too monolithic      | M        | §9 has 9 states from `.unknown` through `.installingChezmoi`. Probing, signed-pkg installation, fallback-binary verification, quarantine-strip, SHA verification, retry/skip UI logic — three responsibilities. | 3.1.4  | `SubprocessRunner` is not its own module  | L        | Foundation for every service. §11 mentions it under `Services/` but module breakdown is implicit. ### 3.4 Plugin host

Out-of-process, JSON-RPC over stdio, manifest-declared capabilities, trust
controls (cosign signature verification per plugin), per-plugin tier
defaults. Reference plugins to validate the protocol:

1. `mise` (clean JSON CLI: `mise ls --json`).
2. `gh extension`.
3. `krew` / `helm-plugin` for k8s users.

Severity: **H** (per 2.7).

## 8. Open questions / decisions deferred to maintainer

These are real decisions that need a person, not items waiting for spec.

1. **Native-cargo, native-mas timing.** Both are cheap. Should they ship in v1 (proves the plugin protocol shape) or v1.1 (saves bandwidth for harder gaps)?
2. **Plugin trust model.** cosign verification per plugin requires the user to manage a trust list. Is the v1 plugin host signature-required, signature-optional-with-warning, or unsigned-allowed?
3. **Default secret broker order.** When both `op` and an age key are present, which does Sojourn prefer? The audit recommends 1Password primary, age fallback. The maintainer may have a different opinion based on the homelab/single-user case.
4. **Discover pane scope.** Live cfprefsd watcher inadvertently captures every preference change anywhere. Is it: (a) opt-in-per-domain recording, (b) global recording with redaction, (c) something else?
5. **History retention.** `deletions.db` is 30d per design. Is push/pull history also 30d, longer, forever?
6. **Per-machine override format.** chezmoi's `promptOnce` vs Sojourn's `.sojourn/machines/<id>.toml`. Audit recommends the chezmoi-native path; maintainer may keep the Sojourn-side metadata for fleet-management features that don't fit chezmoi's model.
7. **OSV/GHSA fetch frequency and feed source.** Daily refresh is in §7. Source: `api.osv.dev` only, or also GitHub Security Advisories direct?
8. **Conflict shapes spec.** `ARCHITECTURE.md` mentions "six shapes" implicitly via design. Enumerate before `CONFLICTS.md` is published.
